## Native recovery storage foundation (not yet connected to Today)

October 4 follow-up after `2b1ab5b`: `apps/mobile/lib/foodNoteRecovery.ts` and `nativeFoodNoteRecovery.ts` add an opt-in storage primitive for reviewed drafts, uncertain saves and uncertain removals. The adapter uses existing Expo SecureStore with WHEN_UNLOCKED_THIS_DEVICE_ONLY and SHA-256 keys scoped to Clerk instance, API origin and account. Session identity is checked before and after asynchronous boundaries. Reads never call the API or claim a save, removal, eating event or inventory change. Saves retain their exact note ID/revision; removals retain only an ID. Allowlisted note fields exclude original media, tokens, dietary data and unrelated supplied fields. Serialized UTF-8 data is bounded to 1900 bytes; oversized drafts fail rather than truncate.

Per-key queues serialize writes and discards across instances. An already-started old-session write can finish only under its original account/environment key; its result is withheld, and queued stale operations cannot clear another session's recovery. Unknown/invalid data and timestamps older than 24 hours or ahead of the local clock are withheld for explicit review/discard, not silently treated as an empty saved state. The 24-hour threshold is a restore eligibility limit, **not automatic erasure**: encrypted records remain until deliberate discard. Retention, sign-out/account deletion and expired-uncertainty handling must be integrated and reviewed before enabling this storage in the UI.

## Today device recovery integration

Check/Keep opens explicit consent describing device/account/environment scope, original-media exclusion, 24-hour restore eligibility and sign-out not erasing copies. Kept content is shown for review, then separately restored; replacing an on-screen draft requires confirmation. Existing/expired/invalid records are not overwritten by Keep. While reviewing uncertain/unreadable device data, note writes are blocked. Discard device recovery removes only the local copy, disables recovery for that visit and reloads account notes; cancelled/failed discards preserve the copy and controls. No local data is read automatically on screen entry. Users must explicitly check a kept copy on return.

When enabled for the visit, a reviewed save/removal checkpoints its immutable request identity before API dispatch. Failure or loss of focus/session during that wait prevents dispatch. Restoration never calls a write: uncertain saves keep the same ID/revision and reload checks the exact dated receipt before any explicit retry; uncertain deletions restore only the blocking warning and require deliberate review. Confirmed operations and successful warning/draft discards clear device storage. Failed cleanup retains conservative uncertainty, even if the account write succeeded; no duplicate automatic retry or false saved claim occurs. Today is keyed by account **and session**, so same-account session replacement also resets transient state. Unsaved typing does not autosave: Keep stores a deliberate snapshot; later edits need a replacement or the explicit Save action's checkpoint.
